0001: # Tensix Performance Counters Guide
0002: 
0003: This guide documents the interface for controlling and reading Tensix hardware performance counters. It covers how to configure and read them from C++ and Python, which useful derived metrics you can compute, and how to test both the interface and the metrics. It consolidates the hardware documentation and aligns it with the implemented interfaces found in this repository.
0004: 
0005: ## Overview
0006: 
0007: Tensix cores contain five hardware performance counter banks (also referred to as "groups" in some hardware documentation). This guide consistently uses the term "bank".
0008: 
0009: | Bank | Description |
0010: |------|-------------|
0011: | INSTRN_THREAD | Instruction issue counts and stall reasons per thread |
0012: | FPU | FPU and SFPU operation valid signals |
0013: | TDMA_UNPACK | Unpacker busy signals and math pipeline status |
0014: | L1 | NoC ring transactions and L1 arbitration events |
0015: | TDMA_PACK | Packer busy signals and destination register access |
0016: 
0017: Each category has debug registers for control and two output registers:

--- around line 63 ---
0055: | 2 (Continuous, no ref) | Same as mode 0, but does NOT maintain the reference cycle count. |
0056: 
0057: **Mode 0 vs Mode 2:** Both run continuously until stopped. Mode 0 tracks elapsed cycles in `OUT_L` (needed for rate calculations), while mode 2 omits reference cycle tracking. **Use mode 0 for most cases** since you typically need both event counts and cycle counts. Mode 2 should only be used when cycle counts are not required.
0058: 
0059: **Note:** The reference period register is ignored in modes 0 and 2.
0060: 
0061: ### Counter Slots
0062: 
0063: A "counter slot" is a single 32-bit configuration word in the per-thread L1 configuration buffer. Each slot (one config word) specifies which bank/counter/mux combination to read out after measurement. The interface supports up to 86 slots per thread, allowing you to capture multiple events in a single measurement window. Slots are processed in increasing index order; invalid slots (valid bit = 0) are skipped and produce no output entry.

0019: # Terminology

--- around line 29 ---
0021: Here are explanations of important terms used throughout entirety of this doc:
0022: - **LLK API** or just **API** &rarr;Low-Level Kernel API provided as header-only library defined in `tt_llk_*` folders of this repo.
0023: - **test** &rarr; pair of `Python` and `C++` files that levarage some part of testing infrastructure to evaluate LLK code.
0024: - **performance test** &rarr; pair of `Python` and `C++` files that levarage some part of testing infrastructure to evaluate some performance characteristic of the kernel code (number of clock cycles needed to execute it etc.).
0025: - **kernel** &rarr; `C++` code compiled to `elf` files for `UNPACK`, `MATH` and `PACK` tensix units.
0026: - **parameter** &rarr; group of arguments passed to `@parametrized` decorator present before test's `Python` function. This decorator is defined in [param_config.py](../../tests/python_tests/helpers/param_config.py).
0027: - **variant** &rarr; tuple of concrete argument values passed as part of one invocation of test's `Python` function.
0028: - **stimuli** &rarr; binary blob generated by one of our custom Torch Golden generators defined in [golden_generators.py](../../tests/python_tests/helpers/golden_generators.py)
0029: - **template parameter** &rarr; compile time, constexpr value generated by `Python` and placed in variant's `build.h` to be passed as template parameter to LLK API function call.
0030: - **runtime parameter** &rarr; values that are passed to API calls as function arguments, `Python` generates a struct that bundles all runtime parameters together. Furthermore, they are loaded to L1 and consumed by all kernels.
0031: - **coverage** &rarr; code coverage information collected during kernel execution which is then processed into `html` report.
0032: 
0033: # Overview
0034: 
0035: LLK testing infrastructure uses `Python`, more specifically it's testing framework called `pytest` to enumerate test variants from tests provided, compile necessary artefacts, and evaluate whether test kernels produce results in expected error bounds. Kernels themselves are written in `C++` using LLK API, and are compiled using our custom RISC-V compiler, called [`SFPI`](https://github.com/tenstorrent/sfpi), into `elf` files that are loaded to and executed on device using this test infrastructure's runtime.
0036:

0038: 
0039: They are used to check if tests written using LLK API perform valid calculations on provided stimuli data. Furthermore, [coverage](https://about.codecov.io/resource/what-is-code-coverage/) information can be collected during kernel execution to see what part of the API was used line-for-line.
