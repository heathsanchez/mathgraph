> ### #2591 vs #2590 — comparative review
> 
> Both PRs actually share the **same central insight**: stop regenerating the _entire_ screen stack on every reload, and only rebuild the screen you're looking at. The difference is what they do about the hidden screens that consequently don't get refreshed — and that difference is the whole story.
> 
> #### What each does with the core idea
> 
> **#2591** (alerque's original, resubmitted; byte-for-byte the same code, targeting the `hledger1` branch) rewrites `regenerateScreens` itself so it only rebuilds the active screen (`aScreen`) and leaves `aPrevScreens` untouched — with **no compensation**. Since `regenerateScreens` is the universal update path (every toggle, filter, period change, drill-down, _and_ reload), hidden screens simply go stale. Pop back to a parent after a reload and you see pre-reload data until you reload again on that level. It also drops the `cur:`/commodity-symbol query re-expansion on reload, and (because its base predates the fix) reverts `listMoveToIfDisplayItems`, reintroducing the #2476/#2550 wrong-selection bug if merged to main.
> 
> **#2590** keeps `regenerateScreens` intact (full-stack regen) for all the toggle/filter/drill-down paths, and adds a _separate_ `regenerateCurrentScreen` used only by reload. To handle the hidden screens it doesn't refresh on reload, it converts every "exit to parent" handler to a new `popScreenAndRegenerate`, which rebuilds the revealed screen from the current journal **at pop time** — lazy, just-in-time refresh. I verified that conversion is complete: there's no path that reveals a stale parent. It also keeps the `cur:` re-expansion and `listMoveToIfDisplayItems`.
> 
> So: **2590 is the more complete realization of the same idea.** 2591 has the navigation-history correctness gap that 2590 explicitly closes.
> 
> #### Likely to fix the leak?
> 
> - **2591** is the strictness/bang-pattern approach jupj already tested (as #2473): it _reduced but did not eliminate_ the register-drill-down memory growth, and gave no CPU improvement. So: partial mitigation, known-incomplete.
> - **2590** additionally cuts per-reload work — sitting on a transaction screen while the file changes no longer rebuilds the big hidden register/accounts reports each cycle, only when you go back. That's a real CPU/allocation win the strictness-only approach doesn't offer. But its strictness is `seq`/WHNF at the screen boundary (no bang patterns on the actual list construction), so leak-fix _completeness_ is unproven from the diff and needs the same empirical test jupj ran.
> 
> Neither can be declared a full fix without re-running both documented repros (repeated `g`, and the append-loop) and watching memory/CPU.
> 
> #### Behavioral risk
> 
> - **2591**: stale navigation history after reload (described above) — a genuine regression, broad because it's on the universal update path.
> - **2590**: one behavioral _change_ to evaluate — `popScreenAndRegenerate` regenerates on **every** back-navigation, not just after a reload. Selection survives by identity (account name / transaction `tindex`), but the exact scroll/viewport offset may not, and large accounts get slight latency on LEFT where `main` was instant. This may be acceptable (always-fresh on back) but it's a maintainer call. Edge case: 2590's `tsUpdate` shows a blank transaction if the account's transactions all vanish.
> 
> #### Other notes
> 
> - **2590 scope creep**: it bundles an unrelated `hledger-lib/Hledger/Utils/IO.hs` change (`embedFileRelative` → manual UTF-8 embed) that touches how every embedded file is read at compile time. Nothing to do with #1825 — should be split out.
> - **Both** reference `reportSpecExpandSymQueries`, which `main` renamed to `reportSpecExpandCurQueries`, so both need a trivial rename to build against current `main`.

Some more commentary re #2590, #2591, and the new #2652 (moved here to consolidate).

> is there another, more robust solution ? The original strategy of regenerating all the hidden screens at once seems simplest and most reliable - if we could completely prevent the retaining of old data
> 
> This is the right question to ask. Both 2590 and 2591 are essentially working around a laziness/retention problem rather than eliminating it.
> 
> Three findings stand out:
> 
> The leak is a thunk chain. Each reload's regenerated list computes its selection index lazily from the previous generation's list (rsUpdate: newselidx ← listSelectedElement oldlist; asUpdateHelper: selidx ← _assSelectedAccount ass). Unforced, generation N+1 pins N, which pins N−1 — a chain growing one link per g. That's both the memory growth and (via GC thrashing / repeated re-evaluation) the pegged CPU.
> Everything else is clean — bounded event channel, old journal released on reload, no caches/IORefs/brick render cache. So there is no second hidden leak to chase.
> The infrastructure for a robust fix already exists: hledger-lib has complete NFData instances (Journal/Transaction/Posting/Amount) and StrictData; the only un-forced links are those two selection indices plus the no-op tsUpdate.
> This means the user's preferred design is viable: keep regenerating the whole stack, but force the regeneration so each new generation holds no reference to the previous one.
> 
> Why alerque's strictness fix (2473/2591) was only partial:
> 
> brick's GenericList.listSelected :: Maybe Int is a lazy field. So alerque's !l' forces the list to WHNF but not the selection index inside it — and that unforced index thunk (newselidx, computed from listSelectedElement oldlist) is exactly the pointer that pins the previous generation. The chain survives. That matches jupj's report that the fix reduced but didn't eliminate the growth.

I'm hopeful that 2560 will solve the issue on all platforms. I have tested only on mac, please test on other platforms if you can. A number of us made substantial contributions pushing this forward, so if it meets the bounty criteria, I'll split the bounty equally.
